# Overview

![[undraw_server-status_7viz.svg|376]]


We have three Docker hosts:

```text
node-one
node-two
node-three
```

Each machine is currently independent.
Docker is running on all three, but nothing connects or coordinates them yet.

In this guide, we're going to change that.
We'll create our first Docker Swarm:

```text
Docker Swarm

node-one      Manager
node-two      Worker
node-three    Worker
```

By the end, all three machines will belong to the same cluster.


---

# Create Our First Swarm

A Docker Engine isn't automatically part of a Swarm.
Swarm mode needs to be activated.

We'll start with:

```text
node-one
```

and turn it into our first **manager node**.

---

## Find the Manager's IP Address

On `node-one`, run:

```bash
hostname -I
```

You should see an address similar to:

```text
172.16.108.130
```

Your address will likely be different.
Keep this address nearby.
The other nodes will use it to find and connect to our manager.

> [!IMPORTANT]
> Use the IP address that `node-two` and `node-three` can reach over the virtual network.

---

# Decide Our Swarm Roles

We currently have three independent Docker hosts:

```text
node-one        node-two        node-three
Docker          Docker          Docker
```

They are **three separate servers**, not three separate applications.
Later, our applications will run *on* these servers.

For our first Swarm, we'll give the machines these roles:

| Machine | Swarm Role |
|---|---|
| `node-one` | Manager |
| `node-two` | Worker |
| `node-three` | Worker |

There is nothing inherently special about `node-one`.
We're **choosing** it to be our manager.
We could choose any of our three machines, but using `node-one` makes our lab easy to follow.

Conceptually, we're about to create:

![[docker-swarm-node-manager-creation.png]]

The **manager coordinates the Swarm**.
The **workers receive and execute work** assigned by the manager.
Later, we might tell the manager:

> "Keep two replicas of my web application running."

The manager can then schedule those replicas onto available nodes.
So before continuing, remember:

> **Nodes are our machines.**
> **The manager coordinates those machines.**
> **Services are the applications/workloads we'll eventually run across them.**

Now that we've decided `node-one` will be our first manager, we can create the Swarm.

---
# Initialize the Swarm

On `node-one`, run:

```bash
docker swarm init --advertise-addr <node-one-IP>
```

We just created our Docker Swarm.

![[docker-swarm-created-terminal-results.png]]

Notice that Docker Swarm assigned a port at the end of our IP.
	Port `2377` is used for Swarm management communication.

[Docker Docs - Create a Swarm](https://docs.docker.com/engine/swarm/swarm-tutorial/create-swarm/)

---

# Theory: The Join Token

Notice that Docker gave us a command containing:

![[docker-swarm-token-terminal-results.png]]

This is a **join token**.
A machine needs the appropriate token before it can join the Swarm.

Docker creates separate tokens for:

```text
Worker nodes
Manager nodes
```

The command shown after `docker swarm init` uses the **worker token**, because Docker assumes we want to add workers next.

> [!WARNING]  
> **Don't store join tokens in your notes, Git repository or screenshots that will be shared publicly.**  
>  
> Treat them as secrets. A node that can reach the manager and has the appropriate join token can use it to authenticate when joining the Swarm.

You don't need to manually save the join token somewhere.
If you lose the worker join command, we can display it again from the manager:

```bash
$ docker swarm join-token worker
```

[Docker Docs - Join nodes to a Swarm](https://docs.docker.com/engine/swarm/join-nodes/)


---

# Add Our First Worker

Now move to:

```text
node-two
```

Run the **exact worker join command** generated by `node-one`.

It will look similar to:

```bash
docker swarm join \
  --token SWMTKN-1-... \
  172.16.108.130:2377
```

Don't copy the example token above. Use the token generated by **your manager**.

Docker should respond:

```text
This node joined a swarm as a worker.
```

Our cluster now looks like:

```text
Docker Swarm

node-one      Manager
node-two      Worker
```

`node-two` is no longer an independent Docker host.

Its Docker Engine is now participating in our Swarm.

---

# Add Our Second Worker

Move to:

```text
node-three
```

Run the **same worker join command**:

```bash
docker swarm join \
  --token <your-worker-token> \
  <node-one-IP>:2377
```

Docker should again respond:

```text
This node joined a swarm as a worker.
```

We now have:

```text
Docker Swarm

node-one      Manager
node-two      Worker
node-three    Worker
```

Success

We've created our first **three-node Docker Swarm**.

---

# Verify the Swarm

Return to:

```text
node-one
```

Remember that `node-one` is our manager.

Run:

```bash
docker node ls
```

You should see something similar to:

![[docker-swarm-docker-node-ls-command-results.png]]

Let's break this down.

| Column | Meaning |
|---|---|
| `HOSTNAME` | Name of the node |
| `STATUS` | Whether Docker can communicate with the node |
| `AVAILABILITY` | Whether the node can receive tasks |
| `MANAGER STATUS` | Manager role/status, if the node is a manager |

Our manager shows:

```text
Leader
```

because `node-one` is currently the manager responsible for leading our Swarm.

The worker nodes have an empty `MANAGER STATUS` because they aren't managers.

---

## What Does the `*` Mean?

You may notice an asterisk next to one of the node IDs:

```text
xxxxxxxxxxxxxxxxxxxxxxxxx *
```

The `*` identifies the node from which we're currently running the command.

Since we're running:

```bash
docker node ls
```

on `node-one`, the asterisk appears next to `node-one`.


---

# Verify Swarm Mode

We can also inspect Docker itself.

On `node-one`, run:

```bash
docker info | grep Swarm
```

Look for the Swarm section.

You should see information indicating:

```text
Swarm: active
```

along with information about the current node and cluster.
The three Docker Engines now belong to the **same cluster**.


---

# One Important Limitation

Our current Swarm contains only:

```text
1 Manager
```

That means we've created a working multi-node Swarm, but we **haven't made the manager layer fault tolerant**.

If `node-one` becomes unavailable, our existing worker tasks can continue running, but we lose the manager needed to perform Swarm management operations.

This is the **single point of failure** we discussed in:
[Docker - Understanding Docker Swarm (theory)](<Docker - Understanding Docker Swarm (theory)>)

Later, we can explore why production environments commonly use multiple manager nodes.
For now, one manager makes it much easier to see how managers and workers interact.

# What Did We Learn?

We started with three independent Docker hosts:

```text
node-one
node-two
node-three
```

We then:

1. Initialized a Swarm on `node-one`.
2. Made `node-one` the manager.
3. Received a worker join token.
4. Joined `node-two` as a worker.
5. Joined `node-three` as a worker.
6. Verified the cluster using `docker node ls`.

But our Swarm isn't doing anything useful yet.
We have the **cluster**.

Next, we need to give it some **work**.

# What's Next?

Until now we've started containers using commands such as:

```bash
docker container run
```

But Swarm introduces a different way of describing applications:

> **Services**

Instead of manually choosing a machine and starting a container there, we'll tell the **Swarm manager what we want running**.

The manager can then schedule that work onto nodes in our cluster.
